# Stats Explorer

[Watch the desktop walkthrough](stats-explorer-demo.webm) (demonstration runs, not live player data).

The append-only `.leaderboard.log` contains runs not yet folded into the archive; include it when backing up the room store.

The Stats menu explores **finished solo runs with a final deck**, including finished one-player rooms. Existing rows without a deck cannot be reconstructed. All run modes, victories, and defeats are eligible. Averages use runs with recorded floors, completed combat stats, and pooled incoming damage respectively; the damage value is dealt **per fight**. Next-card deltas compare otherwise-filtered decks with and without a card. They are observational, not causal, and have no minimum confidence interval.

The room server alone classifies finished decks. **GPT-6 Sol with high reasoning** inspected the board game's rules and all 37 eligible submitted solo decks at initial seeding (anonymized, grouped by character) to produce an initial list of **nine** evidence-backed archetypes; characters without submitted decks have no seeded types. The known decks are assigned their archetypes once by exact deck hash and matching character, creating real rows and sample decks immediately; these assignments never override a type already recorded for a run. Unused legacy speculative seeds are removed during migration even when the archive has classified runs or pending retries; referenced classified names and newly discovered types are preserved. The server runs `codex exec` with `gpt-6-sol`, high reasoning, and a read-only sandbox inside its deployed game codebase. For every archetype of the submitted deck's character, the classifier compares the submitted deck with up to **three distinct classified sample decks** of that type before choosing an existing type or creating a new one. Codex sees card names, upgrades, counts, socketed Guardian Gems, bounded game-defined rules/text, and sample cards, not player names or IDs; it can inspect game code to understand synergies. It persists newly discovered names and the thread ID privately alongside the run archive. Subsequent decks resume that thread, including after a server restart; a new code release starts a fresh thread so it reads the current rules. To bound model input, it sends up to 50 distinct variants of the incoming cards and up to 40 card variants per sample, reporting omitted-card counts; oversized incoming summaries are trimmed to 20,000 characters, and large catalogs keep every candidate type while reducing sample detail to stay under 100,000 characters. Classification runs asynchronously after submission (and resumes pending decks on restart), so gameplay never waits for AI. There is **no public AI route**; `/api/stats` and `/api/stats/deck` only read aggregated or already-stored finished solo data. Submissions cannot set their own type. Pending decks appear in the matching-run total but not an archetype row until classification succeeds.

Only runs reaching floor 15 can establish a new specific archetype. Shallower runs (or runs without a recorded floor) join an existing archetype when it fits, or their character's `Other` group. If that character has no specific archetype yet, the server assigns `Other` without using AI or requiring a Codex login. Its first floor-15+ deck must receive a specific archetype even if `Other` already exists. A run initially labeled `Other` because its floor was unknown is reconsidered if a later submission establishes that it is the character's first floor-15+ deck.

On the **local room-server machine**, install `bwrap` and the Codex CLI. Sign in with **ChatGPT**, not a Platform API key, using the server user's dedicated Codex home:

```sh
CODEX_HOME="$HOME/.local/share/slay-the-spire-server/codex" codex login --device-auth
CODEX_HOME="$HOME/.local/share/slay-the-spire-server/codex" codex login status
```

The worker requires the npm-distributed Codex CLI (`npm install -g @openai/codex`): `STS_CODEX_BIN` must resolve to its `bin/codex.js`, not a standalone native binary.

Device-code login requires approval in the user's browser; use `codex login` with the same `CODEX_HOME` for browser-based sign-in instead. The worker rejects API-key login even if the host CLI is authenticated with one, and never copies the host's `~/.codex/auth.json`. Its private mode-0700 directory contains writable ChatGPT credentials (so Codex can refresh tokens) and persistent thread sessions. The Codex CLI can access this home, but its model-directed tools use a read-only permissions profile that **denies reads of the entire Codex home**. The deployed systemd unit enables classification and points `STS_CODEX_BIN` at the CLI; other operators can configure `STS_DECK_CLASSIFIER_ENABLED=true` and their own binary path. The worker exposes only read-only game code, CLI files, the Node runtime, CA certificates and its own credential/session directory to the CLI, not the live room store, multiplayer tokens, or other application files. Do not put credentials in the repo or a public route. Codex inherits no application secrets from the room server.

Without ChatGPT authentication or `bwrap`, the archive remains readable and decks needing AI wait for classification; shallow decks with no existing specific type still enter `Other`. Restart the room-server service after signing in. Back up the room store, its `.leaderboard.json` archive, and its `.stats.json` and `.stats.log` sidecars together; the latter preserve archetypes, the private thread ID, and attempt limits across rollbacks. The server retries transient failures after a minute without blocking other runs; missing Codex authentication stops attempts and refunds the reserved daily slot. Output-token failures defer only the affected deck until the next UTC day, retaining a resumable thread if one was started. Missing or full existing contexts reset the thread before retrying; a first-turn full context instead defers the deck without retaining that thread. Classification uses a persist-before-request **global 100-attempts-per-UTC-day cap**, including retries, to bound model usage from unauthenticated submissions; the server operator can set `STS_DECK_CLASSIFICATIONS_PER_DAY` to a different nonnegative integer for their traffic and budget. Run data containing unknown card IDs, impossible upgrades, or invalid Gem attachments is omitted from Stats and never sent to Codex.

The visual filter builder combines `ALL` cards with an `ANY` group and excludes `NONE` cards. Cards from every hero remain searchable even when filtering runs to one hero, since cross-hero decks are possible. The Expression tab accepts parentheses and `and`, `or`, `not`, e.g. `(Dual Cast or Dual Cast+) and not (Strike or Strike+)`. A name shared by multiple heroes matches the corresponding card for any of them, including attached Guardian Gems; `@strike_defect` matches only Defect Strike (either upgrade). The search also recognizes “Explosive Corps” as a hint for the actual Silent card, **Corpse Explosion** (including its upgrade). The Ascension menu supports all levels, exact levels 0–13, or any level **i+** for i = 0–10; it composes with hero, mode and card filters. Selecting a next-card result requires the card (either upgrade) without discarding the active filter. Pending results can be refreshed manually or update automatically every 15 seconds while the tab is visible, including after a temporary network error. All queries and deck samples are evaluated server-side against finished decks; the server never returns raw installation IDs or usernames on these endpoints.
