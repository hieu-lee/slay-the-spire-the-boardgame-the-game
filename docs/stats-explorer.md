# Stats Explorer

[Watch the desktop walkthrough](stats-explorer-demo.webm) (demonstration runs, not live player data).

The append-only `.leaderboard.log` contains runs not yet folded into the archive; include it when backing up the room store.

The Stats menu explores **finished decks**. All single modes includes solo Standard, Daily, and Custom runs; multiplayer decks appear only with the separate Multiplayer filter and never affect single-player averages or card comparisons. Existing rows without a deck cannot be reconstructed. Victories and defeats are eligible. Averages use decks with recorded floors, completed combat stats, and pooled incoming damage respectively; the damage value is dealt **per fight**. Multiplayer damage and block use each player's recorded combat totals, never the party's combined totals. Older room decks without per-player combat stats contribute to multiplayer counts, floors, and card comparisons, but not damage or block averages. Next-card deltas compare otherwise-filtered decks with and without a card. They are observational, not causal, and have no minimum confidence interval.

The room server alone classifies finished decks. **GPT-6 Sol with high reasoning** inspected the board game's rules and all 37 eligible submitted solo decks at initial seeding (anonymized, grouped by character) to produce nine evidence-backed archetypes. A subsequent Codex CLI review of the first floor-20 Hermit deck and three floor-13 Hermit decks added **Hermit Curse-Chamber Payoffs** as a tenth seeded archetype for the floor-20 deck; the shallow decks remain **Hermit Other**. The known decks are assigned their archetypes once by exact deck hash and matching character, creating real rows and sample decks immediately; these assignments never override a type already recorded for a run. Unused legacy speculative seeds are removed during migration even when the archive has classified runs or pending retries; referenced classified names and newly discovered types are preserved. The server uses `@openai/codex-sdk` to start and resume local Codex CLI threads with `gpt-6-sol`, medium reasoning, and a read-only sandbox inside its deployed game codebase. For every archetype of the submitted deck's character, the classifier compares the submitted deck with up to **three distinct classified sample decks** of that type before choosing an existing type or creating a new one. Codex sees card names, upgrades, counts, socketed Guardian Gems, bounded game-defined rules/text, and sample cards, not player names or IDs; it can inspect game code to understand synergies. It persists newly discovered names and the thread ID privately alongside the run archive. Subsequent decks resume that thread, including after a server restart; a new code release starts a fresh thread so it reads the current rules. To bound model input, it sends up to 50 distinct variants of the incoming cards and up to 40 card variants per sample, reporting omitted-card counts; oversized incoming summaries are trimmed to 20,000 characters, and large catalogs keep every candidate type while reducing sample detail to stay under 100,000 characters. Classification runs asynchronously after submission (and resumes pending decks on restart), so gameplay never waits for AI. There is **no public AI route**; `/api/stats` and `/api/stats/deck` only read aggregated or already-stored finished deck data. Submissions cannot set their own type. Pending decks appear in the matching-run total but not an archetype row until classification succeeds.

Only runs reaching floor 15 can establish a new specific archetype. Shallower runs (or runs without a recorded floor) join an existing archetype when it fits, or their character's `Other` group. If that character has no specific archetype yet, the server assigns `Other` without using AI or requiring a Codex login. Its first floor-15+ deck must receive a specific archetype even if `Other` already exists. A run initially labeled `Other` because its floor was unknown is reconsidered if a later submission establishes that it is the character's first floor-15+ deck.

On the **local room-server machine**, install `bwrap` and the npm-distributed Codex CLI (`npm install -g @openai/codex`). The bundled SDK reuses the server user's **existing local Codex CLI login**; no separate server login is needed. Check it with:

```sh
codex login status
```

The SDK still requires an authenticated local CLI; it cannot run models without credentials. It uses the CLI's existing ChatGPT or API-key sign-in, never a public route. For API-key operation, the systemd unit can load `OPENAI_API_KEY` from the optional, private `%h/.config/slay-the-spire-server/codex.env` file (owner-only permissions; `OPENAI_API_KEY=<your key>`). The local worker signs into the CLI from this variable when its cached API key differs or is absent, without another manual login. This updates the **shared** `~/.codex/auth.json`: it replaces any existing ChatGPT sign-in with API-key billing, and removing the environment file does not restore that sign-in; use `codex login` to switch back. `STS_CODEX_BIN` must resolve to the npm CLI's `bin/codex.js`, not a standalone native binary.

The worker binds the user's existing `~/.codex` into an isolated Codex home for authentication and resumable sessions; model-directed tools **cannot read that home**. The sandbox sees only read-only game code, the CLI runtime, system certificates, and the SDK's temporary output schema, not the live room store or multiplayer tokens. The deployed systemd unit enables classification and points `STS_CODEX_BIN` at the CLI; other operators can configure `STS_DECK_CLASSIFIER_ENABLED=true` and their own binary path. Do not put credentials in the repo or a public route. The server's API key reaches only the local worker's login step through its environment; the worker removes it before launching Codex turns, and no other application secrets are forwarded.

Without a local CLI login or `bwrap`, the archive remains readable and decks needing AI wait for classification; shallow decks with no existing specific type still enter `Other`. Restart the room-server service if the local CLI login changes. Back up the room store, its `.leaderboard.json` archive, and its `.stats.json` and `.stats.log` sidecars together; the latter preserve archetypes, the private thread ID, and attempt limits across rollbacks. The server retries transient failures after a minute without blocking other runs; missing Codex authentication stops attempts and refunds the reserved daily slot. Output-token failures defer only the affected deck until the next UTC day, retaining a resumable thread if one was started. Missing or full existing contexts reset the thread before retrying; a first-turn full context instead defers the deck without retaining that thread. Classification uses a persist-before-request **global 100-attempts-per-UTC-day cap**, including retries, to bound model usage from unauthenticated submissions; the server operator can set `STS_DECK_CLASSIFICATIONS_PER_DAY` to a different nonnegative integer for their traffic and budget. Run data containing unknown card IDs, impossible upgrades, or invalid Gem attachments is omitted from Stats and never sent to Codex.

The visual filter builder combines `ALL` cards with an `ANY` group and excludes `NONE` cards. Cards from every hero remain searchable even when filtering runs to one hero, since cross-hero decks are possible. The Expression tab accepts parentheses and `and`, `or`, `not`, e.g. `(Dual Cast or Dual Cast+) and not (Strike or Strike+)`. A name shared by multiple heroes matches the corresponding card for any of them, including attached Guardian Gems; `@strike_defect` matches only Defect Strike (either upgrade). The search also recognizes “Explosive Corps” as a hint for the actual Silent card, **Corpse Explosion** (including its upgrade). The mode menu offers solo Standard, Daily, and Custom decks, plus a Multiplayer option for all room decks; All single modes excludes multiplayer. The Ascension menu supports all levels, exact levels 0–13, or any level **i+** for i = 0–10; it composes with hero, mode and card filters. Selecting a next-card result requires the card (either upgrade) without discarding the active filter. Pending results can be refreshed manually or update automatically every 15 seconds while the tab is visible, including after a temporary network error. All queries and deck samples are evaluated server-side against finished decks; the server never returns raw installation IDs or usernames on these endpoints.
